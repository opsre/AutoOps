01 / WHY

运维不缺工具，缺的是把它们连起来的那一层

Zabbix 管监控、ELK 管日志、JumpServer 管登录、KubeSphere 管容器、CMDB 单独一套、工单又是另一张表——每多一套系统，就多一套账号、一份数据孤岛、一段对不上的时间线。

01
系统割裂告警在 A、日志在 B、主机在 C、工单在 D。定位一次故障要开五个窗口，时间戳还对不上。
02
告警风暴工具只负责"发出去"，不负责"收敛"。同一台主机八条告警刷屏，真正的根因被淹没。
03
变更失控SQL 直连生产、脚本随手执行、发布靠人盯。出事只能翻聊天记录：没审批、没回滚、没录像。
04
AI 只是聊天框大模型接进来了，却拿不到资产、读不到日志、动不了工单——问完还得人肉去别的系统里操作。

传统做法：6 ~ 8 套系统拼装

Zabbix / Prometheus + Grafana账号 ①
ELK / EFK 日志栈账号 ②
JumpServer 堡垒机账号 ③
KubeSphere / Kuboard账号 ④
CMDBuild / 自研 CMDB账号 ⑤
Archery / Yearning SQL 审计账号 ⑥
自研工单 / 发布系统账号 ⑦
独立 AI 工具账号 ⑧
结果：资产要同步 8 次、权限要配 8 遍、故障要查 8 个地方，且没有任何一条链路是通的。

04 / DIFFERENTIATION

六个别人不容易补齐的结构性优势

不是"我们也有"，而是"这些能力只有在同一个数据模型里才成立"。每一条都能在源码里找到对应实现。

01

真一体化：不是集成，是同一份数据

很多平台说"集成"，本质是 iframe 嵌页面、API 拉数据。AutoOps 是同一套数据库、同一套资产 ID、同一套权限：主机在 CMDB 建一次，监控、告警、日志、终端、工单、AI 诊断全部直接引用。

  • 告警 → 主机详情 → 指标曲线 → 进程/端口 → 终端登录，一条路径到底
  • 资产变更自动反映到所有下游模块，没有"同步任务"要维护
  • 角色授一次，12 个域的菜单、按钮、接口动作同时生效
统一主数据12 域共享模型单一 RBAC
02

AI 在流程里干活，不在旁边聊天

内置 MCP Server，把 CMDB、K8s、日志、监控能力注册成标准工具；14 个技能按风险等级分级（只读 / 低风险 / 需确认），AI 调用有审批、有留痕、可回放。

  • 问"这台机器为什么慢"——AI 自己查指标、拉日志、看进程，再给结论
  • 危险动作（重启、执行命令）走二次确认，不会"自作主张"
  • Agent Run / Step / 证据全程落库，出了问题能倒查是哪一步判断错了
  • Web 端 + 企业微信双入口，值班在手机上也能问
MCP 工具协议风险分级 SkillRun 审计企微入口
03

变更安全闭环：从"敢改"到"可回滚"

运维事故大多不是"发现不了"，而是"改了之后回不去"。平台把数据库变更做成完整工单：提交 → 自动审核 → 审批 → 执行 → 一键回滚（集成 gh-ost / my2sql / pgroll 等工具）。

  • DML / DDL / 查询三类工单，审批节点可自定义
  • 执行前影响行数预估，执行后 binlog 留档
  • 发布单支持分项执行、失败重试、实时日志
  • 所有变更与操作日志、终端录像串联，审计时是一条完整证据链
SQL 工单审批流回滚发布单
04

混合环境原生支持：VM + K8s + DB + 网络设备

大多数平台只能选一边：要么传统主机（Zabbix 系），要么纯云原生（KubeSphere 系）。国内现实是两套并存——物理机跑核心库，K8s 跑新业务，还有交换机和中间件。

  • 六云主机导入（阿里/腾讯/华为/百度/AWS/天翼）+ 机房机柜 U 位管理
  • K8s 全资源控制台 + 容器终端 + 文件管理 + Arthas 诊断
  • SNMP 交换机监控、Kafka/ZK/ES/Nginx 中间件运维
  • Windows 主机（Exporter 远程安装 + 远程桌面）同样纳入
六云K8sSNMP中间件Windows
05

可观测底座更轻：VictoriaMetrics / VictoriaLogs

不堆 Elasticsearch 集群，不做"日志平台要 3 台 32G 起步"的架构。Vector 采集 + Kafka 缓冲 + VictoriaLogs 存储，单机即可承载中小规模生产日志，指标侧用 VictoriaMetrics 兼容 PromQL。

  • 兼容 Prometheus 生态：现有 exporter、Grafana 面板可直接复用
  • 日志字段检索、上下文查看、链路追踪视图、日志告警
  • 采集配置由平台统一下发，K8s 采集器一键安装
  • 慢日志自动分析 + 日报，DBA 不用天天手工捞
PromQL 兼容低资源占用统一采集
06

交付就绪：能进内网，能上 ARM，能离线

ToB 项目最怕"演示很漂亮，交付一地鸡毛"。AutoOps 从第一天就按私有化交付设计：一键 compose、双架构镜像、离线 Agent、机器绑定授权。

  • ./devops-start.sh v5.0 <ip> 8080 一条命令拉起全套
  • amd64 / arm64 双架构镜像，适配信创与国产化环境
  • 被管端 Agent 支持离线打包，无外网也能采集
  • License 机器绑定 + 离线激活，功能按域授权
一键部署ARM64离线 Agent离线授权

一句话总结差异：Zabbix 解决"我知道出问题了"，ELK 解决"我能查到日志"，JumpServer 解决"谁能登机器"。AutoOps 解决的是"从发现问题到安全地改完，全程在一个地方、留一条证据链"。

SCENE 01
值班问答

"支付服务昨晚是不是有抖动？"——AI 自动对齐时间窗，拉指标、告警、日志，给出时间线而不是一段废话。企业微信里直接问，不用开电脑。

SCENE 02
根因定位

告警进来先由 AI 做第一轮收敛：同一宿主机的 8 条告警归并成 1 个事件，附上最可能的根因与证据，值班只看一条。

SCENE 03
变更辅助

慢 SQL 分析给索引建议、发布前给出风险清单、变更后对比指标基线。所有建议都标注数据来源，不黑箱。

可审计，才敢用。每一次 AI 调用都记录：用了哪个技能、调了哪些工具、拿到什么数据、做了什么动作、谁确认的。安全团队可以像查操作日志一样查 AI——这是「能进生产」和「只能演示」的分水岭。

架构简单到一个人能维护，能力却覆盖全栈

09 / FAQ

选型时最常被问到的六个问题

和直接上 Zabbix + ELK + JumpServer 比，省下的钱够覆盖平台成本吗？

这三套系统本身免费，但成本在别处：服务器资源（ELK 尤其重）、至少 3 套的部署与升级维护、跨系统的账号与权限对齐、以及每次排障时人工拼接时间线的时间。AutoOps 用一套应用 + 一个 MySQL + 一个 Redis 起步，日志与指标底座用 VictoriaMetrics/VictoriaLogs，单机即可承载中小规模数据；真正的节省来自"少维护 5 套系统"和"排障链路缩短"。建议用你们现有的主机数、日志量、值班人力做一次对照测算。

我们已经有一套 Prometheus 和 exporter，需要推倒重来吗？

不需要。指标侧兼容 PromQL，现有 exporter 与采集方式可以保留，AutoOps 作为查询、告警、展示与流程层接入；日志侧支持标准采集协议，可先双写并行验证。平台的价值在于把指标与资产、日志、变更、工单关联起来，而不是替换你的采集端。

AI 会不会乱操作生产环境？

不会。技能按风险分级：只读类（查资产、查指标、查日志）可直接执行；写操作（执行命令、重启、变更）必须走二次确认，并且确认人、动作、参数、结果全部落库。所有 Agent 运行都有 Run/Step 记录与证据引用，可回放、可追责。你也可以选择只启用只读技能。

私有化部署后，AI 功能还能用吗？

可以。LLM Provider 在平台内配置（支持 OpenAI 兼容协议及国内主流模型服务），既可接入内网自建模型，也可配置代理访问外部 API；不配置模型时，平台的监控、日志、堡垒机、工单等能力完全不受影响。

支持国产化 / 信创环境吗？

支持 ARM64 架构（提供 arm64 镜像与一键部署脚本），可运行在国产 Linux 发行版上；被管端 Agent 支持离线打包，适合无外网环境。具体 OS 与芯片组合建议在 POC 阶段做一次适配验证。

数据量和规模上限在哪？

单体架构在 500~2000 台主机、日志 50~200 GB/天的量级内表现良好（取决于硬件与保留周期）。超过这个量级建议把 VictoriaMetrics / VictoriaLogs / Kafka 独立部署并横向扩容，应用侧可多副本 + 前置负载均衡。超大规模（万台以上）建议先做专项压测评估。
